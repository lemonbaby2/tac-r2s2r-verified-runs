# Datasheet — TAC-R2S2R verified GPU runs

This datasheet follows the *Datasheets for Datasets* template (Gebru et al.,
*Communications of the ACM*, 2021). It documents the released artifact:
**160 seeded runs of a controlled synthetic sim-to-real transfer proxy** for the
TAC-R2S2R framework (Li & Chen, 2026).

---

## 1. Motivation

**For what purpose was the dataset created?**
To provide mechanism-level, fully reproducible evidence for the *paired
consistency* component of the TAC-R2S2R framework, and to release the raw
seed-level records behind the accuracy / risk / Brier numbers reported in the
manuscript (Table IV). It exists so that a third party can re-derive every
headline number from the released files without re-training.

**Who created it and who funded it?**
Zipeng Li and Jing Chen, School of Physics and Optoelectronic Engineering,
Guangdong University of Technology, Guangzhou, China. No external funding is
declared for this artifact.

**Any other comments?**
This is a **controlled synthetic mechanism test**, not a physical-robot
experiment, not a vision-language-action (VLA) policy training run, and not a
complete Real2Sim2Real benchmark. See §5 for the exact claim boundary.

---

## 2. Composition

**What do the instances represent?**
Each *run* is one training + evaluation of a 30–96–48–1 MLP on a synthetic
binary grasp-and-place proxy over a fixed source-domain budget, for one of four
methods and one seed. Evaluation is on 8,192 freshly generated target-domain
samples per run.

**How many instances are there?**
- `data/run_metrics.csv` — **160 rows** = 4 budgets × 4 methods × 10 seeds.
- `data/summary.csv` — **16 rows** = budget × method aggregates (mean ± 95% t-CI, df = 9).
- `data/training_history.csv` — **14,400 rows** = 160 runs × 90 epochs.
- `data/paired_contrasts.csv` — paired (TAC − TW) contrasts per budget.
- `data/verified_runs.json` — structured snapshot: 2 GPU records, 16 aggregates,
  160 per-run records (with confusion matrices, 10-bin calibration, 90-epoch history).

**What data does each instance consist of?**
Per run: device name, CUDA UUID, budget, method, seed, wall-seconds,
`target_success_rate` (binary classification accuracy on 8,192 target samples —
**legacy name, not robot success**), `unsafe_confident_error_rate` (share of
samples misclassified with p ≥ 0.8 or p ≤ 0.2), and `brier_score`.

**Is there a label or target?**
Yes: a binary label `y = 1[m > 0]` where `m` is the synthetic margin (Eq. 16 of
the manuscript). Labels are generated by a fixed program, not by humans or
sensors.

**Is any information missing?**
The target-domain `shift` and `scale` slots are **blank in the manuscript**; the
released run uses the **per-dimension** values from the original implementation
(`shift = [0.35,-0.25,0.45,0.20,0.30,-0.35]`,
`scale = [1.10,0.90,1.20,1.05,1.15,0.95]`, label noise σ = 0.30). These are the
values that reproduce Table IV; see `VERIFICATION.md`.

**Are relationships between instances made explicit?**
Runs share the same generator and seeds; `id = {budget}_{method}_{seed}` joins
`run_metrics.csv` to `training_history.csv`.

**Are there recommended data splits?**
The 2,048-sample target *validation* split uses seed offset +700000; the 8,192
target *test* split uses +900000. Both are deterministic and re-derivable from
`code/run_task_aware_transfer.py`.

**Any errors, sources of noise, or redundancies?**
Label noise σ = 0.30 is intentionally injected. Run-to-run variance comes from
the ten seeds; no run is duplicated.

**Is the dataset self-contained?**
Yes — the generator is a fixed program included in `code/`. No external data,
downloads, or credentials are needed to regenerate the data.

## 3. Collection Process

**How was the data acquired?**
By executing `code/run_task_aware_transfer.py`. Two machines each ran one half
of the seeds (5 seeds each) so that the two halves ran on **two physically
distinct GPUs** (CUDA UUIDs recorded to prove it).

**Who collected it and how were they compensated?**
The authors, as part of preparing the manuscript. No crowd-workers.

**Over what timeframe?**
The 2026-11-02 verified re-run; each 80-run sweep takes ≈ 75 s of wall clock.
The 2026-11-11 independent cross-check re-ran all 160 runs on an NVIDIA GB10
(89.9 s wall); see `supplemental/gb10/` and `VERIFICATION.md`.

**Were ethical review / consent obtained?**
Not applicable — no human subjects, no personal data, no robot operation.

---

## 4. Preprocessing / Cleaning / Labeling

**Was any preprocessing/cleaning/labeling done?**
No manual cleaning. Features are generated on the fly by the fixed program.
Labels are computed analytically from the margin. Aggregates in
`summary.csv` use a two-sided 95% Student-t interval (df = 9); the `_ci95`
columns are **half-widths** (interval = mean ± value).

**Was the "raw" data saved?**
Yes — seed-level records are the raw artifact (`run_metrics.csv`,
`training_history.csv`). Aggregates are derived and can be recomputed by
`code/verify_numbers.py`.

**Is the software used to preprocess/clean/label available?**
Yes, in `code/`, standard-library only for verification.

## 5. Uses

**What tasks could the data be used for?**
- Reproducing / auditing the manuscript's Table IV numbers.
- Studying the stability of task-weighted vs uniform domain randomization as a
  function of source budget (the TW@2048 collapse is the key negative result).
- Teaching reproducibility and honest reporting boundaries.

**Is there anything that should NOT be done with the data?**
- **Do not** interpret `target_success_rate` as physical robot task success. It
  is binary classification accuracy on synthetic samples.
- **Do not** cite the single-global-shift *inferred* reproduction as the paper's
  result (it inflates TW@2048 to ≈ 92.55%; the faithful value is ≈ 58%).
- **Do not** treat this as evidence about a VLA policy, a real robot, or a full
  Real2Sim2Real pipeline.

**Any risks?**
Low. No personal or sensitive data. The main risk is **misinterpretation** of
the legacy field name and over-generalizing a synthetic mechanism test to robot
performance.
